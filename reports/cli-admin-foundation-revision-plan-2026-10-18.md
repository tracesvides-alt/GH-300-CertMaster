# 第3段階：CLI操作・管理権限を確認する基礎問題の見直し計画

計画日：2026-10-18（日本時間）

[第2段階の実施結果](cli-admin-reference-expansion-2026-10-18.md)を受け、既存の基礎6問を候補として、CLI操作3問、プラン・管理権限3問の順に見直す。今回は計画の作成であり、問題・解説・教材の変更は実施していない。

## 目的と範囲

用語名の識別に偏っている問題を、短い利用場面からCopilotの操作・管理範囲を選ぶ問題へ改善する。基礎では一つの中心的な判断を問う。応用の複合条件や高難度の多段階推論は持ち込まない。

通常出題253問、基礎162・応用48・高難度43を維持する。D1 24・D2 98・D3 33・D4 35・D5 32・D6 31の配分も維持する。対象6問はいずれも現在の分類が基礎・D2である。問題IDの見た目ではなく、現在のdifficulty・domainId・objectiveIdを基準にする。

新規問題の追加、削除、他ドメインへの移動、応用・高難度の書き換えは含めない。対象外の問題と、先に訂正した問題・教材を一括生成で変更しない。

g09で具体的な追加ディレクトリ指定を問う場合は、教材の既存補足にも入力例と条件を添える。追加ディレクトリはファイルアクセスだけでなく信頼する設定の読み込みにも関係するため、「モデルの記憶量を増やすだけの指定」とは教えない。起動オプションと対話中の操作の両方が正解にならないよう、問題文で入力場所を指定する。

管理問題では、Copilotプラン、GitHubの契約・アカウント、操作する人のロール、対象範囲を明記する。組織のレポートと企業のレポート、組織の監査ログとEnterprise監査ログを取り違えない。

候補となる根拠は、[公式プラン一覧](https://docs.github.com/en/copilot/get-started/plans)、[企業のプラン選択](https://docs.github.com/en/copilot/tutorials/roll-out-at-scale/assign-licenses/choose-enterprise-plan)、[Copilot usage metrics API](https://docs.github.com/en/rest/copilot/copilot-usage-metrics)、[Copilot監査ログ](https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-for-enterprise/review-audit-logs)。問題作成時に該当する操作の公式節まで再確認する。

「ログやレポートを読めるので、シートやポリシーも変更できる」といった権限の推測を正解にしない。一般の請求管理や一般のGit操作へ出題の軸を移さず、Copilotの管理場面を判断する問題にする。

## 3. 問題・選択肢・解説の品質基準

各問について、以下を個別に記録する。自動的な文字数判定だけでは合格にしない。

1. **元の概念との対応**：関連用語の中心概念を正しく理解して答える問題か。用語を問題文へ置いただけで対応を維持した扱いにしない。
2. **日本語**：誰が、どの画面・入力場所で、何をしたいかを自然に読めるか。「資格」「許可」「文脈」等を省略して意味を曖昧にしない。不要な事例名や条件は足さない。
3. **ブラインドチェック**：問題文を隠すと、選択肢がいずれも成立し得る用途・操作か。正解だけが具体的・丁寧・安全そう、誤答だけが極端、という構成を避ける。
4. **一意性と反実仮想**：現在の条件では正解が一つで、入力場所・目的・権限等の中心条件を変えると別の選択肢が適切になるか。架空のコマンドや存在しない権限名を誤答の主力にしない。
5. **難易度**：短い場面から一つの基本操作・権限を選べるか。権限の継承、複数の資格提供元、ツール設定の優先順位等を重ねて応用化しない。基礎として基本知識から解けること自体は欠点としない。
6. **重複**：対象6問だけでなく、導入・ログイン、非対話実行、再開、ツール制御、シート管理、利用レポート、監査の既存問題と、正解に必要な判断・条件の組み合わせを比較する。
7. **長さと正解位置**：選択肢の長さ、語調、説明量を比較する。正解だけが長い・具体的にならないようにする。局所的な正解位置の調整のために、他の問題は変更しない。
8. **解説**：Why this is correctには、問題中の条件→機能・権限の仕組み→正解になる理由→適用の限界を自然な文章で記す。選択肢ごとの解説は短くする。削除済みのKey Cluesは復活させない。

実装時にはまずCLI3問の草案を作り、この基準でレビューする。その後に管理3問を作成する。レビュー不合格の問題は修正し、元の概念を失わずに改善できない場合は候補から外して理由を報告する。対象を無断で広げない。

## 4. 保存済み履歴と既存検証を壊さない実装

現在は原本と改訂差分を照合して表示する仕組みがあるため、その方針を継続する。第1・第2段階の台帳は過去の記録として保持する。

- 作業開始時の有効問題・解説・教材・関連リンク・用語対応を記録する。
- 新しい改訂は専用の差分台帳へ保存し、対象外の問題や既存の改訂を巻き込まない。
- 問題文・選択肢・正解・解説を同じ版として扱う。現行と異なる保存済みの版へ新解説を組み合わせない。
- 古い回答は当時の問題・採点情報と整合させる。旧問題を新しい演習へ混ぜない。正解IDが同じでも問題の意味が変わる場合は、版を確認する。
- 新たな改訂が古い版のテストを置き換えないよう、段階間の変更前後を照合する検証を追加する。過去の指紋を新しい値へ上書きするだけの対応はしない。
- 用語のbasicQuestionId、Lessonの関連問題、公式出典の参照を確認する。既存監査の中には原本だけを読むものもあるため、改訂後の有効問題でも検査する。

対象6問はsingle-selectを維持する。多肢選択の数や仕様は変更しない。構造・履歴表示のコード変更が必要な場合は、該当するNext.js同梱ガイドを読んでから最小限の変更を行う。

## 5. 演習対応の台帳を更新する

第2段階の参照表39項目の評価は、正解12・関連場面6・誤答のみ8・未出題13だった。改訂後には項目ごとに再評価し、変更前後の分類と対応問題IDを記録する。

特に、用語の名称が正解であることと、操作や権限を正解として選べることを区別する。個人プランについて一問改善しただけで全7プランを確認済みにしたり、組織のMetrics閲覧を問う問題で企業のbilling managerまで確認済みにしたりしない。

今回の候補で優先するのは、限定したCLIの実行許可、追加ディレクトリ、個人プランと管理ロール、組織の利用レポート閲覧、Enterprise監査ログ閲覧。既に正解として確認できるCLIの起動も失わないようにする。

`/model`、`/permissions show`、`/compact`・`/clear`、企業の利用レポート閲覧、企業管理下のプラン選択、監査ストリーム設定等は、この6候補ですべて解消するとは扱わない。残る不足は優先度とともに記録し、増問で自動的に埋めない。

## 6. 検証と完了条件

| 検証 | 完了条件 |
|---|---|
| 個別レビュー | 対象各問に出題概念、ブラインド判定、反実仮想、誤答の理由、日本語・難易度・長さの評価がある |
| 教材との一致 | 正解に必要な操作・権限が教材から学べ、教材の条件と矛盾しない |
| 公式根拠 | 改訂する正解・解説の事実に出典と確認日がある。実装時点で再確認する |
| 問題データ | ID・難易度・ドメイン・Objective・出題形式を保持し、対象外問題が変わっていない |
| 用語対応 | 関連用語6件の基本概念への対応を確認する。数値上のリンク維持だけで合格にしない |
| 履歴 | 新旧の問題・回答・解説が混ざらず、旧回答を開いても矛盾しない |
| 自動検証 | 型、データ、解説の版照合、出題数・配分、関連リンク、問題品質の検証が通る |
| 画面 | PC・スマートフォンで、教材からの演習開始、正誤表示、解説、履歴・復習を確認する |
| 対応台帳 | 39項目について、改善した箇所・維持した箇所・残る不足を区別できる |

既存のテストがこの段階の対象をカバーしているか確認し、新しく変更した判断・版管理の挙動に必要なテストを追加する。単に問題文の文字列を写すテストだけにしない。本番ビルドでの表示も確認する。

完了時は、日本語の結果レポート、問題別レビュー、変更前後の台帳、演習対応の差分、実施した検証と残る不足を報告する。Gitへのcommit・pushやデプロイは、この計画に含めない。

## シラバスとの位置付け

[Microsoft Learn GH-300 Study Guide](https://learn.microsoft.com/en-us/credentials/certifications/resources/study-guides/gh-300)と既存のObjective対応を確認し、Copilotの利用・管理を学ぶ範囲として扱う。現行CLIの細かなコマンドを扱ったことを、実試験の全出題を再現した根拠にはしない。

CLIへのContent Exclusionの公式資料間の説明差は今回の正解判定へ持ち込まない。教材の既存の要レビュー状態も、この作業を理由に検証済みへ変更しない。
