# GH-300 全200問の難易度再評価

## 結論

従来の難易度は適切とは言えなかった。Foundationの基本知識確認は維持できる一方、Appliedには操作の記憶問題、Examには長い状況説明を付けただけの機能名識別が含まれていた。選択肢のもっともらしさと、解答に必要な思考の深さは別に評価する必要がある。

全200問の本文・4選択肢・解説を参照し、90問を実質改稿、54問を下位へ再分類した。総数と正答IDは維持。表示順だけの変更は改稿数に含めない。

| 難易度 | 変更前 | 変更後 | 判断基準 |
| --- | ---: | ---: | --- |
| Foundation | 44 | 80 | 用語・機能・原則・操作の識別 |
| Applied | 79 | 78 | 具体的な入力・不具合・用途へ知識を適用 |
| Exam | 77 | 42 | 証拠や処理段階を比較し、原因・未検証条件・最小変更を導く |

## 何を難しくしたか

- 文の長さ、専門用語の多さ、選択肢へ付けた点数を難易度の根拠にしない。
- Appliedでは具体的な期待値、モックの境界、移行時の互換性などを選ばせる。
- Examではログ・設定・契約・検証結果の関係を読み取る。各問に二段階以上の判断と、条件を変えたとき別の判断になる反例を記録した。
- 共有シナリオに属するという理由だけでExamにしない。用途識別の問題はFoundationへ戻した。
- 元の20/40/40という問題数の比率は維持しない。低難度問題を比率合わせのために昇格させない。

### q-d1-e01: Exam → Exam

変更前: あるスタートアップの開発者が、Copilotに高度な画像処理関数の実装を依頼したところ、`import { processUltraHDR } from 'fast-hdr-toolkit';` というパッケージをインポートするコードが提案されました。ビルド時に「パッケージが見つからない」とエラーが出ました。セキュリティエンジニアが最も警戒すべきリスクと取るべき措置はどれですか？

変更後: Copilotが画像処理の依存PとQを提案しました。Pは機能テスト成功・既知脆弱性0件ですが、公開は昨日で発行元未確認です。Qは承認済みの発行元・署名一致ですが、指定の色変換テストに失敗します。採用基準は出所確認と必要な機能の両方です。各候補の判断は？

評価: 別パスの再読で、文言の照合や明らかに無関係な誤答を避けて追加修正。候補ごとに出所と機能の証拠を分類する → 一方の成功で他方の未確認を補えないと判断する

条件を変えた場合: Pの発行元も確認済みならPは採用可能となり、Qだけが機能確認待ちになる。

### q-d2-e06: Exam → Exam

変更前: Agentを導入するチームは、削除や外部通信の実行前に内容を確認する運用を求めています。設定の違いによる承認の省略も考慮して実施すべきことは？

変更後: Copilot CLIの権限演習です。セッションPはshellツールが利用可能で、Git操作を許可しgit pushだけ拒否しています。Qは利用可能ツールを読取系だけに制限し、Git操作の許可も指定しています。denyはallowより優先し、許可指定は利用可能ツールを増やさない規則です。P・Qでcommitとpushを行うと？

評価: 別パスの再読で、文言の照合や明らかに無関係な誤答を避けて追加修正。利用可能ツールと実行許可という二層を分ける → PとQそれぞれの有効範囲を求める

条件を変えた場合: Qにshellを利用可能として追加すれば、QのGit許可が働きcommitとpushの両方が可能になる。

### q-d3-e02: Exam → Exam

変更前: 金融機関の社内インフラにおいて、すべての外部通信に対して社内プロキシによるSSL復号（SSL/TLS Inspection）が強制されています。開発者がVS CodeでCopilotを起動したところ、`certificate verify failed: unable to get local issuer certificate` というエラーが発生して接続できません。インフラチームと開発チームが連携して実施すべき、セキュリティ基準を満たす正しい対処はどれですか？

変更後: 同じアカウント・同じ社内プロキシを使うPCを比較しました。PはHTTP CONNECT成功後にissuer certificateエラーで、提示証明書は社内CAです。QはCONNECTに対し407 Proxy Authentication Requiredとなり、接続先の証明書はまだ受け取っていません。両者の最初の確認をどう分けますか？

評価: 別パスの再読で、文言の照合や明らかに無関係な誤答を避けて追加修正。各PCが到達した通信段階をログから追う → TLSの信頼とプロキシ認証を別の修復対象へ割り当てる

条件を変えた場合: QもCONNECT成功後のissuerエラーなら、両方でCA信頼設定を調べる案が合う。

### q-d5-e01: Exam → Exam

変更前: 生成したテストはタイマーで更新される状態を500ms待って確認します。CIでは時々失敗し、テスト中のタイマーは制御可能です。速さと再現性を改善する指示は？

変更後: Copilotが生成したdebounceのテストを見直します。仕様は最後の入力から300ms後に1回保存です。t=0で入力A、t=200で入力Bを与えました。偽タイマーを使い、非同期更新完了も待つ前提で、仕様違反の早期保存と最終保存をともに検出する検証は？

評価: 単純な機能選択・条件の言い換えでは足りない証拠比較へ改稿。最終入力時刻から発火境界を計算する → 境界前後と保存引数を組み合わせて不具合を検出する

条件を変えた場合: 入力がAだけなら、299msで0回・300msでAの1回が適切。

### q-d6-e05: Exam → Exam

変更前: 休眠シートを回収する運用を自動化したいが、活動情報が欠けた利用者を誤って解除したくありません。適切な手順は？

評価: 単純な機能選択・条件の言い換えでは足りない証拠比較へ改稿。二つの日付条件を各利用者へ適用する → 不明値を無活動へ変換せず別の処理へ分ける

条件を変えた場合: 不明値を追加調査してDの最終活動が45日前と判明すれば、Dも候補になる。

### q-sc09-1: Exam → Exam

変更前: 【Nexis Games事例】受容率と生成行数は増えましたが、割り込みや疲労が減ったか不明です。予算内で次の測定を一つ追加し、既存の活動指標を補完したい。SPACEを踏まえた選択は？

条件を変えた場合: 人数が不変で手戻り率も低下していれば、観測上の改善という報告を支持する。

## 検証方法と限界

全200問の初回の難易度評価に続き、改稿90問の本文・全選択肢を別パスで再読した。単位の誤記、計測指標の分母、明らかに無関係な通信対策の選択肢などを追加修正した。同じ編集者のレビューであり、独立した別人による評価ではない。

この評価は問題が要求する認知操作の分類である。実際の学習者の正答率・解答時間・識別力は未測定で、実試験と同じ難しさだとは断定できない。Foundationは正しく理解した学習者には易しくてよい。Examも全問を難問にするのではなく、基礎知識だけの問題と区別する。

自動検査は内容指紋、分類、根拠、回答ID、回答後のヒント、全件網羅を確認する。根拠欄の存在やテスト成功だけで設問の意味的品質を証明するものではない。問題を変更したら再読して台帳を更新する。

共通シナリオの文脈・問題IDと保存済み解答との対応は維持した。ただし、文面を改稿した問題の過去の正答率は改稿前の成績であり、新問の実測難易度として解釈しない。
