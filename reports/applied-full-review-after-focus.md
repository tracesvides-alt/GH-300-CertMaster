### q-d1-a02：生成保証の誤学習

問題文の「安全な…のみを生成するように制約」、正答の「強制」、解説の「直ちに生成」「最も効果的」は指示で保証できる印象を与える。共通指示も個別生成へ影響するのでBの否定を一般化しない。

改善方向：安全な方針・スキーマ・例を与えて生成を誘導し、出力の検査で適合を確認する判断へ修正。個別と共通と検出の役割を候補として残す。

根拠：[About customizing GitHub Copilot responses](https://docs.github.com/en/copilot/concepts/prompting/response-customization)。指示の結果は非決定的。共通指示は対象内の依頼に文脈を与え、個別関数に影響しないと一般化しない。
根拠：[Copilot inline suggestions: responsible use](https://docs.github.com/en/copilot/responsible-use/inline-suggestions)。指示や生成結果への依存だけで安全性・正確性を保証せず、生成コードをレビュー・検証する必要を確認。

### q-d1-a04：多層防御だけが正解に見える／防御の保証表現

Aだけが指示とPush対策を両立する。他案は部分対策や補完停止。解説の「強制」「Pushを自動阻止」は全資格情報・全経路を必ず防ぐ印象を与える。

改善方向：確認済みの入力・PR・Pushの保護と、今回未保護の経路を示し、同程度に現実的な補完策から選ばせる。指示の誘導と検知対象・設定・バイパスを区別する。

根拠：[Copilot inline suggestions: responsible use](https://docs.github.com/en/copilot/responsible-use/inline-suggestions)。指示や生成結果への依存だけで安全性・正確性を保証せず、生成コードをレビュー・検証する必要を確認。
根拠：[Push protection](https://docs.github.com/en/code-security/concepts/secret-security/push-protection)。検知対象・設定・バイパスによる範囲があるので、どんな資格情報でも全経路で防ぐとは扱わない。

### q-d1-a07：極端な誤答／レビュー設定の前提

ジュニアだけ、シニア免除、無人マージという誤答が露骨。自動レビューの有効設定と組織の人間承認規則を明記せず一般化している。現行Docsには設定で有効にするCopilot approvalsの公開プレビューもある。

改善方向：自動レビュー有効、人間承認必須という組織規則を前提に、通知・コメント・承認・必須チェックのどこが不足かを問う。製品機能の可否と組織の方針を混同しない。

根拠：[About GitHub Copilot code review](https://docs.github.com/en/copilot/concepts/agents/code-review)。自動レビューには設定が必要。通常のレビューと、設定で有効になるCopilot approvals公開プレビュー、組織の人間承認規則を分ける。

### q-d2-a04：実行前プレビューだけが安全に見える

履歴を隠す、バックグラウンド実行するという誤答は安全な検証候補にならない。一般的な削除の常識で正答を推測しやすい。

改善方向：対象一覧は確認済みだがパス境界・追跡外の保存対象・実行段階のどれが未確認かを観測から選ぶ。四案とも現実的な実行前検証へそろえる。


### q-sc05-2：実体照合だけが完成した検査

同じ自由モックの入力・戻り値変更や名前保存に対して、実SDKの型と正式契約だけが独立した確認になっている。

改善方向：各案に独立した検査を持たせ、API存在・引数・結果・失敗経路のどの不整合を現在のモックが隠すかで選ぶ。


### q-d3-a09：正答だけにCopilot Chatの接続先

Git SSH、PCへの受信、社内DBという誤答では、選択肢のサービス名だけでChatを選べる。本文で既に宛先・方向・プロトコルを明示しており、実質的な難度も基礎寄り。

改善方向：同じCopilot通信の別の宛先・方向・段階を候補にし、接続診断の成功と失敗を組み合わせて必要な許可だけを選ぶ。D3の枠は維持する。

根拠：[Troubleshooting network errors for GitHub Copilot](https://docs.github.com/en/copilot/how-tos/troubleshoot-copilot/troubleshoot-network-errors)。通信先・経路・証明書の確認を別の層として扱う。

### q-d2-e14：正答だけが整ったエージェント工程

実装を見ない、相互依存を競合解決なしでコミット、全文一括置換という誤答で、分業・引継ぎ・テストを含む正答を読み解く前に選べる。

改善方向：四案とも調査・実装・テストを行い、依存関係や共有文脈の引継ぎがどこで足りないかを具体的な観測から判断させる。


### q-d5-a07：時計ループ・形式だけのassertという誤答

固定時刻・時間帯・境界の正答に対し、実時間ループと形式だけの検査は露骨。UTCで固定すればローカル時間帯の仕様やDSTも検証できると受け取らないようにする。

改善方向：業務の時間帯と検証する境界を明示し、四案とも固定した実行環境を用意する。どの期待値や時間帯が仕様と合うかで選ぶ。「タイミグ」も修正する。


### q-d5-a14：決済再送の前提不足／危険な誤答

接続切断では決済が成功済みで応答だけ失われた可能性があり、一過性エラーだから再送してよいとは限らない。キャッシュで決済完了とする案やデバッグURLの返却も露骨な誤答。「AIが…含みやすい傾向」の根拠も台帳の一般例外Docsでは不足。

改善方向：対象APIの再送契約、結果不明時の照会、冪等性キーなどの前提を明記し、再送と返却情報のどちらが未対策かで選ぶ。特定APIを使うと勝手に仮定しない。

根拠：[Stripe API: idempotent requests（一般実装の参照例）](https://docs.stripe.com/api/idempotent_requests)。書込再送ではAPIの契約を確認する必要があることの一次資料の例。設問のAPIがStripeだと仮定したりGH-300公式教材のSource of Truthへ追加したりするものではない。

### q-d5-a15：整数制約の明示不足／弱い誤答

正答は型・範囲のスキーマと17/18/文字列18を挙げるが、数値スキーマに整数制約があることと18.5の拒否を明示していない。型numberとmin18だけでは小数が通る。「網羅的」も過大。

改善方向：型・整数・下限をそれぞれ検証し、小数・負数・境界・文字列の期待結果を明示する。誤答は入口検証を持ち、条件一つの欠落として比較する。


### q-d1-e06：審査を続ける案だけが妥当に見える

履歴・依存だけ・CodeQLを採用断片のライセンス審査の代用にする誤答は、具体例がなくても消去できる。

改善方向：全案で採用審査を続け、参照断片・依存・契約・設定のどの情報が未確認かを実例から判断する。D6の出力保護という出題軸を保つ。


### q-sc05-3：前回23問のうち残る主題・重複の問題

機密情報とトークンの除去は本文で完了しており、四択はどのログ構成で要求経路を追うかを問う。q-sc03-3も同じ経路情報を選ぶため、プライバシーの判断が選択を分けていない。

改善方向：q-sc03-3を文脈取得の基準問として維持。q-sc05-3は匿名化後に必要な相関を残す範囲と不要な再識別情報を区別する問いへ寄せる。全案を機密を除去した妥当な資料案にし、D6の枠を維持する。
